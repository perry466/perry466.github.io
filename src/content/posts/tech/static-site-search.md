静态站点做搜索，只有两条路：把内容交给第三方（Algolia、各种搜索云服务），或者在构建时自己生成索引。

后者更省心，代价是「要构建才能测」。

## 构建期切片

思路不复杂：构建完成后扫描所有 HTML，把正文切成小段，为每段建倒排索引，输出成一组静态文件。浏览器端加载一小段 WASM，在本地完成查询。

所以搜索是完全离线的，没有网络请求，也没有内容离开你的仓库。

## 索引的代价

| 项目 | 观测值（20 篇全文） |
| --- | --- |
| 索引体积 | 约 1.2MB（压缩后传输） |
| 构建耗时 | 0.3–0.5 秒 |
| 首次搜索延迟 | 首次需下载索引，之后无感 |

索引体积随文章数线性增长，但压缩率很高，中文内容尤其明显——重复的常用字多。

## 中文的实际限制

英文搜索能靠词形还原把 read / reading / reads 归到一起，中文没有这层。所以：

- 「构建」搜不到「构建期」以外的变体，除非文章里真的出现过
- 单字查询噪音很大，两个字以上才实用
- 拆词质量取决于索引器，业务术语（如「内容集合」）常被切开

> [!NOTE]
> 如果你的站点只有几十篇文章，浏览器的 `Ctrl+F` 加上归档页其实已经够用。搜索框不是必需品，它是在「文章多到看不过来」之后才有价值的东西。

## 什么时候值得引入

我的判断标准是三十篇。低于这个数，读者更可能通过分类和标签找东西；高于这个数，一个能高亮命中词的搜索框会明显减少退出率。

引入之后记得在文章正文容器上加索引标记，否则导航、页脚、侧栏都会被切成垃圾片段，索引体积翻倍而命中质量下降。
