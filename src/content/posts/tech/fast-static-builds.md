构建时间从 47 秒压到 19 秒，中间试过七八件事，真正有效的只有三件。记录一下，免得下次又从头试一遍。

## 先量，再改

不要凭感觉优化。构建日志里每一项都有耗时，先找出占比最大的那一段：

| 阶段 | 优化前 | 优化后 | 手段 |
| --- | --- | --- | --- |
| 图片处理 | 18.4s | 3.1s | 尺寸收窄 + 命中缓存 |
| Markdown 渲染 | 12.7s | 11.9s | 换处理器，收益有限 |
| 页面生成 | 9.2s | 3.4s | 减少重复取数 |
| 搜索索引 | 4.1s | 0.4s | 只索引正文 |

排序之后，优先级一目了然：图片占了一半以上的时间。

## 一、图片：别生成用不上的尺寸

一个封面生成 5 档宽度，而页面最多用到 3 档，多出来的两档就是纯浪费：

```ts
<Image
  src={cover}
  widths={[640, 960, 1280]}
  sizes="(min-width: 1024px) 720px, 100vw"
/>
```

再加上构建缓存，第二次构建时这些图直接命中，几乎不占时间。

> [!TIP]
> 本地开发时把 `widths` 砍到一档，能省掉大部分等待；发布前记得改回来。

## 二、取数：同一份数据只算一次

每个页面都调用一次「取全部文章并排序」，二十篇文章看不出来，两百篇就是重复的几十万次比较。加一层模块级缓存即可：

```ts
let cache: Post[] | null = null;

export async function getAllPosts(): Promise<Post[]> {
  if (cache) return cache;
  cache = (await getCollection("posts")).sort(byDateDesc);
  return cache;
}
```

模块在同一个构建进程里只初始化一次，缓存天然是安全的——静态构建没有「热更新」这种需求。

## 三、搜索索引：别把导航也索引进去

索引器只看带标记的正文容器，页头、页脚、侧栏全跳过。索引体积小了，构建时写入也快：

```html
<div class="article-main" data-pagefind-body>
  <!-- 正文 -->
</div>
```

## 白忙一场的那几件

- 换一个更快的 Markdown 处理器：省了 0.8 秒，配置成本两天。
- 并行度调到 `os.cpus().length * 2`：机器直接卡死，收益为负。
- 关掉所有校验：`check` 从 6 秒变 0，然后花一下午修一个本该被拦住的字段错误。

> 优化的第一原则是知道时间的去向。没有测量的优化，通常只是把等待换了个地方。
