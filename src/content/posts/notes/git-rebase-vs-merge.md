关于 `rebase` 和 `merge` 的讨论经常变成信仰之争。其实只要回答一个问题就够了：**这条分支有没有别人在用？**

## 私人分支：变基

功能分支只有你自己在推，历史随意改写。变基能让提交记录变成一条直线，每个提交都是一个完整的意思：

```bash
git fetch origin
git rebase origin/main
```

出冲突时的处理也比 merge 干净：一次解一个提交，而不是一次解一团。

## 共享分支：合并

`main`、`release`、任何别人已经拉下去过的分支，都不要变基。改写历史意味着别人的本地仓库与远程分叉，之后每次拉取都要处理一堆莫名其妙的冲突。

```bash
git switch main
git merge --no-ff feature/search
```

`--no-ff` 保留一条合并记录，日后追溯「这批改动是什么时候进来的」很方便。

## 一条边界

| 分支 | 有人在用 | 做法 |
| --- | --- | --- |
| 本地功能分支 | 否 | `rebase`，随时整理 |
| 已推送但只有自己 | 否（可强推） | `rebase` + `--force-with-lease` |
| `main` / 发布分支 | 是 | 只用 `merge` |
| 别人的分支 | 是 | 不要动，只读 |

> [!WARNING]
> 用 `--force` 之前先确认没有别人基于这条分支工作。`--force-with-lease` 至少会在远程有意外提交时拦你一下，但它救不了正在别人机器上开发的分支。

真正会上瘾的不是变基本身，而是「提交历史读起来像一篇文章」的感觉。为了这个感觉改写共享历史，代价通常比收益大。
