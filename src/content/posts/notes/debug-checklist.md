排查问题最贵的成本不是「想不出原因」，而是在错误的方向上想了两小时。

下面这个顺序帮我省掉过很多时间，按顺序走，不要跳步。

## 一、能不能稳定复现

不能复现的问题，先不要修。

| 情况 | 该做的事 |
| --- | --- |
| 每次都出现 | 进入第二步 |
| 偶尔出现 | 先找触发条件：数据、时序、并发、缓存 |
| 只在一台机器上 | 先比环境：版本、字体、时区、本地存储 |
| 只在线上出现 | 先比构建产物，不要比源码 |

最后一条最常被忽略。线上跑的是构建后的东西，源码一样不代表产物一样。

## 二、最近改了什么

```bash
git log --oneline -10
```

改完之后开始出问题，这件事本身就是最强的线索，比任何推断都可靠。

如果最近没有改动，就找「环境变了」：依赖升级、服务端配置、浏览器版本、时钟。

## 三、用二分法定位

改动多的时候不要逐个回退，用二分：

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.2.0
```

范围大时它比人工排查快一个数量级。前提是每个提交都能构建——如果一个提交本身就坏，二分会被误导，这时候先修 CI。

## 四、才是读代码

到这一步，问题通常已经被缩小到几十行以内。这时候读代码是有目标的读，而不是从头开始找。

## 一条附加规则

修好之后，补一个能复现它的测试，或者至少留一条注释说明当时的现象。否则三个月后同一个人（你）会重新排查一遍同样的问题。

> 排查的顺序比聪明更重要。方向对了，笨办法也能到；方向错了，快也白快。
